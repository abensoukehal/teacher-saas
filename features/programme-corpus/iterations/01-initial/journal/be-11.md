## B2 — the edition axis

### What QA reported did not reproduce. Two worse things did.

QA's B2 says the loader "keys on `docKey` alone", so a 2023-09 file is either discarded as
unchanged or absorbed into the 2022-09 document by `--correct`, and **"no code path can
ever create a second-edition document."**

That is not what the code does, and I checked before changing anything. `upsertProgramme`
already looked up `findOne({ docKey, edition })`. Against a scratch database
(`qa_edition_probe`, dropped after), on the shipped loader at `33cda9a`:

| probe | observed |
|---|---|
| load lettres 2022-09, then the same file at 2023-09, content identical | **both inserted.** 2023-09 `current:true`, 2022-09 `current:false` |
| fresh db: 2022-09, then 2023-09 with content changed | **both inserted**, same flip |

So the second-edition document QA says is unreachable is what the loader already produced,
and `--correct` could never change an edition because the lookup is keyed on it. I could
not reproduce either half of the stated repro and I am recording that rather than writing a
fix for a defect that is not there.

**But QA's instinct was right, and the real defects are worse than the reported one.** Both
reproduced on the same scratch database, and both exit 0:

**D1 · `current` followed the LOAD ORDER, not the edition.** `demoteOtherEditions` demoted
"every edition that is not the one just written" — its own comment said *"the newest edition
loaded wins"*. So with 2023-09 current, a one-word transcription fix to the 2022-09 file:

```
$ load --file lettres-2022-09-corrected.jsonl --correct --note "typo fix"
load-programmes: corrected tadarroj-3as-lettres @ 2022-09 transcriptionRev=1 → 2
exit=0
→ 2022-09 current:true   ·   2023-09 current:false
```

**Fixing our own reading of an old page silently rewound the syllabus**, and said nothing.
This is the two axes collapsing in the direction nobody watches for: not "a syllabus change
read as a misreading", but "a misreading-fix read as a syllabus change".

**D2 · a mistyped edition was a silent new document.** `edition` was validated as
"non-empty string". `2022-9` for `2022-09`:

```
$ load --file lettres-typo.jsonl
load-programmes: inserted tadarroj-3as-lettres @ 2022-9 transcriptionRev=1 …
exit=0
→ three documents; the typo holds current; the real 2022-09 demoted
```

Identical wording to a first load. A typo entered the corpus wearing the ministry's clothes,
which is the exact confusion SEED §3.1 says the two axes exist to prevent.

### The design I chose, and why

**Support the real flow** — a new edition becomes a new document, the previous flips to
`current:false`, `{docKey, edition}` stays unique. Not the "loud refusal" option, for one
reason: **the loud refusal is what the loader already did to a mistyped edition — nothing —
and that is how D2 got in.** A refusal-only design leaves no correct path, so the first
person to meet a real 2023 edition would reach for `--correct`, which is precisely the
collapse to avoid. The flow already half-existed and the unique index was already there; the
job was to make its edges honest.

Three changes, all in `src/store/programmes.ts` so the CLI holds no second copy of the state
table:

1. **`EDITION_PATTERN = /^\d{4}-(0[1-9]|1[0-2])$/`.** A malformed edition is now a seed error
   (exit 1), not a document. It does two jobs: it kills D2, and it makes editions **totally
   ordered as plain strings** — zero-padded and fixed-width, so lexicographic order *is*
   chronological order.
2. **`reconcileCurrent(db, docKey)` replaces `demoteOtherEditions`.** `current` is now derived
   from the data — the greatest edition wins — instead of from what just happened. That is
   D1's fix, and it is idempotent and order-independent: re-running it reaches the same state,
   and backfilling an *older* edition cannot take `current` either.
3. **`--new-edition` (exit 5 without it).** A file bringing an edition of a docKey we already
   hold is refused until it is declared, and the refusal names every edition already stored
   plus both ways out. Symmetric with `--correct`: a correction needs its audit trail, a new
   edition needs its declaration. **The two flags are refused together** (exit 1) — one says
   "we misread our own page", the other "the ministry revised the programme", and guessing
   which was meant is how one axis becomes two names for the same thing.

**`--correct` still cannot change an edition, and now by two independent means.** It was
already structural (the lookup is keyed on `{docKey, edition}`, so a moved edition never
reaches the correction branch); the new-edition branch now refuses ahead of it as well. A
clause pins each.

Deliberately **not** done: a new edition writes **no** `programme_revisions` row. That
collection records *our* superseded readings; the previous edition is not superseded, it is
still a true record of what the ministry published then, and it keeps its own document. A
revision row would be the two axes collapsing again, in the storage layer this time.

**One accepted sharp edge, recorded rather than fixed.** Inserting a new edition sets
`current:false` on its siblings without first re-hashing them, so it will touch a
hand-edited sibling. That is safe — `current` is in `CONTENT_HASH_EXCLUDES`, so the tamper
is not masked and the sibling still fails its own recompute on its next load — and a full
sibling-integrity scan on every insert is not worth it for a five-document corpus.

## B1 — the maths legend

QA: page 18 prints `هوملّون` as one cluster; the corpus stored `هو ملوّن`. Same class as the
techmath squashes the corpus deliberately preserved (`الأحمرلعدم تناولهفي`).

**Verified independently before touching the seed, with two instruments that agree.**

*The PDF's own text layer* (`pdftotext -bbox`, page 18). The math text layer is
letter-reversed, so each word was reversed to logical order; the cluster decodes as one
token plus its continuation, with the junction measured against the line's real spaces:

```
x[342.53,350.27] gap_to_prev=3.06  ما
x[320.57,339.52] gap_to_prev=3.01  هوملّ        ← a real space before it
x[308.76,320.66] gap_to_prev=-0.09 ون          ← no space INSIDE it
x[282.20,305.76] gap_to_prev=3.00  باللون
```

Codepoints, logical order: `U+0647 U+0648 U+0645 U+0644 U+0651 U+0648 U+0646` —
ه و م ل **ّ** و ن. **The shadda is on the LAM, not the waw.**

*Pixels*, `pdftoppm -r 600`, crop of the same span: one connected cluster, shadda sitting
over the lam. QA called the shadda's base "indeterminate from pixels" and corrected only the
space; at 600 dpi with the crop tight it is legible, and it agrees with the text layer and
with QA's own rendering of the page (`هوملّون`). So the correction is both: the space out and
the shadda on ل.

**The layer-2 re-read already had it right, and `--compare` had been saying so.** The l2 file
was **not** touched — and did not need to be. It stores
`guidanceFirst: "تم ادراج ما هوملّون باللون الأحمر لعدم تناوله في السنة الدراسية 2021-2022"`.
With the l2 file untouched:

```
before:  27 seed weeks, 27 l2 weeks, 112 discrepancy(ies), 0 coverage gap(s)
         week 24 · row[0].guidance · seed "تم ادراج ما هو ملوّن باللون" · page "تم ادراج ما هوملّون باللون الأحمر"
after:   27 seed weeks, 27 l2 weeks, 111 discrepancy(ies), 0 coverage gap(s)
```

The independent reader had flagged this exact cell all along; nobody read past the count.
That is worth more than the fix — **`--compare`'s 111 remaining lines are unread evidence**,
mostly punctuation and word-count noise in the 6-word anchors, but nobody has separated the
noise from the next B1. Recorded as debt below.

**Applied** to `data/programmes/tadarroj-3as-math.jsonl` in both places the string appears —
`emphasisLegend.text` and week 24 row 0's `guidance[0]` — then loaded with a note:

```
load --file … --db teacher_saas --allow-live-db --correct --note "…"
corrected tadarroj-3as-math @ 2022-09 transcriptionRev=3 → 4
  changed: emphasisLegend.text
  changed: weeks[23].rows[0].guidance[0]
```

Two field paths, nothing else — the dry run was checked first and said the same.

**Checked and deliberately NOT changed:** the legend's year, stored `2022-2021`. The l2 file
normalises it to `2021-2022`, and it is outside the 6-word anchor so `--compare` never saw
it. The page prints **2022-2021** — read from pixels at 600 dpi, the digits being exactly
what SEED §2.1 disqualifies text extraction for. The seed is right and the l2 line is the
reader's own bidi normalisation. A clause pins the whole legend string so this cannot be

**M1 survived and is worth reading.** It replaces "greatest edition" with "last document in
Mongo's natural order", which on this data returns the same answer — the editions happen to
be inserted in ascending order. It is an equivalent mutant *for the corpus as it exists*, and
not equivalent in general: backfilling an older edition after a newer one would separate
them, which is why the `an edition EARLIER than the current one` clause exists. M1' is the
same idea written faithfully to the pre-fix code, and it dies. **Kill rate 10/11 as written,
10/10 excluding the equivalent mutant.**

M6, M7 and M9 each take down 12–16 clauses rather than one, which is the shape to want here:
the edition axis is pinned by many small independent assertions, not by one clause that
would go green again with a one-line edit.

**M5 is the one the clause had to be rewritten to catch.** Removing the CLI's early exit
leaves the store's throw, which yields the same exit code and a message matching the same
regex — so as first written, the clause could not tell the two apart and M5 survived it. The
clause now also runs the same command against `mongodb://127.0.0.1:1`, where a check that
needs a connection to fire cannot fire: "refused before a connection is even opened" is
what the clause is named, so it is now what the clause tests. M5 dies on 5 assertions.

### ⚠ A methodology failure worth recording: the mutation harness raced itself

The harness backs a file up to a fixed path, mutates, gates, restores. I ran three batches
in the background and launched the second before the first had finished, so two runs shared
`/tmp/mut.cli.bak` — and one restore put back a copy that had already been mutated. The
result was the CLI's contradiction guard **silently missing from the working tree** while
the gate stayed green at 145/145, because that clause is also satisfied by the store's throw
(exactly what M5 measures).

Caught by diffing every changed file against `main` line by line before committing, not by
the gate. Two things follow, and the second is the real one:

- The mutation harness needs a per-run backup path. It is scratch tooling and was left as
  it is, but never run two batches concurrently against it.
- **A green gate is not evidence that the tree is what you think it is.** After any
  mutate-and-restore campaign, read the full diff. The whole reason M5's clause was
  strengthened is that one layer silently covering for another is invisible from the
  summary line — and that is precisely the shape this near-miss took.
