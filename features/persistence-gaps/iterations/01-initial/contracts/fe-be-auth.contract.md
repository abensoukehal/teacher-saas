# Contract — `fe` ↔ `be` · teacher accounts

> **Status:** locked by `/planning`, 2026-08-08. Derived from SEED → Solution direction #1.
> **Posture: strictly additive.** No existing surface changes shape. `/api/generate`,
> `POST /api/subjects`, `GET /api/subjects`, `GET /api/subjects/:id` and
> `PUT /api/subjects/:id/exercises/:exerciseId` all keep their current request and response
> contracts, so `be` and `fe` can merge in either order — the same property that let the
> `persistence` job land safely.

## The one idea

Sign-in **returns the `teacherId` that already exists**. The browser keeps sending it as
`x-teacher-id` exactly as today. Accounts are a way to *obtain and re-obtain* that id, not a
replacement for it.

Consequences, and why this shape was chosen:

- **Zero document rewrites.** `subjects.teacherId` keeps pointing at the same 32-hex value
  and the `{teacherId:1, updatedAt:-1}` index stays valid (SEED journal H8).
- **The subject routes are untouched**, so their promoted characterization suites stay green.
- **The teacherId remains a bearer credential.** Accepted for this milestone and recorded in
  SEED → Risks. Making it a rotating, expiring session is explicitly *not* in this job; a
  future job replaces the header without touching the store.

## Amendment — anonymous teachers (2026-08-08, decided during `be-2`)

The contract as first written said an id "that was never issued is rejected". `be-2`
exposed the ambiguity: **`POST /api/teacher` issues ids without recording them.** Taking
the strict reading would have locked out all 159 teacherIds that already own subjects,
broken the promoted regression net (its `newTeacher()` calls `POST /api/teacher`), and
broken `fe`, which still calls `issueTeacher()` until `fe-1` ships.

So "issued" means **"minted AND recorded"**, and there are two kinds of teacher row:

| kind | `email` | how it is created |
|---|---|---|
| anonymous | `null` | `POST /api/teacher` — records the row it already minted |
| account | a string | `POST /api/auth/signup` |

Three consequences, all binding:

1. **`POST /api/teacher` now writes a row.** Its response shape is unchanged.
2. **A one-time backfill** creates an anonymous row for every distinct
   `subjects.teacherId` that has none. Without it, rejection is a data-loss event for
   every existing teacher. It inserts into `teachers` only — **no subject document is
   touched**, preserving the zero-rewrite property.
3. **The unique index on `email` must be PARTIAL** —
   `{ unique: true, partialFilterExpression: { email: { $type: "string" } } }`. A plain
   unique index permits only one null, so the second anonymous teacher would collide.

### Sign-up adopts the caller's anonymous id

If the sign-up request carries `x-teacher-id` and that row exists **and has no email**,
sign-up attaches the email and password to **that** row instead of minting a new id.

Without this, a teacher who used the app anonymously and then signed up would get a new
id and silently lose every exam they had made — gap #1 again, caused by its own fix.

- Row is anonymous → adopt it, keep the id, exams follow.
- Header absent, or malformed, or the row already has an email → mint a fresh id.
  (Already claimed means someone is signing up a second account from the same browser.)
- **Sign-IN never adopts or re-points anything.** Merging an anonymous id into an account
  on sign-in would rewrite `subjects` documents, which the SEED's zero-rewrite property
  rules out.

## Storage — the `teachers` collection

```
teachers
  _id           ObjectId
  teacherId     string · 32 hex     ← THE JOIN KEY. Same value subjects.teacherId holds.
  email         string | null       ← null = ANONYMOUS row (see amendment above)
  passwordHash  string | null       ← scrypt, see below; null while anonymous
  recoveryHash  string | null       ← scrypt over the recovery code; null while anonymous
  recoveryUsedAt Date | null        ← WHEN the last code was consumed (informational).
                                    The rotating recoveryHash is what enforces single use.
  createdAt     Date
  updatedAt     Date

indexes:
  { email: 1 }      unique, PARTIAL ({email: {$type: "string"}})  ← one account per
                                    address; partial so many anonymous rows (email null)
                                    can coexist — a plain unique index allows one null
  { teacherId: 1 }  unique          ← the join back to subjects
```

**`teacherId` is generated by the existing `issueTeacherId()`** (`src/teacher.ts:20-22`) —
unchanged, still `randomBytes(16).toString("hex")`. Sign-up writes it down; that single act
is what closes gap #1.

### Password and recovery-code hashing

`node:crypto`'s **`scrypt`** — no new dependency (`be` has 9, none of them a hasher, and
adding one is not justified when the platform ships this).

```
format:  scrypt$N$r$p$<salt-b64>$<derived-b64>
params:  N=16384  r=8  p=1  keylen=32  salt=randomBytes(16)
compare: timingSafeEqual over the derived key — never ===
```

Both `passwordHash` and `recoveryHash` use this exact format so one helper serves both.

## The recovery code

**This is the reset path, and it is why no mail integration is needed.**

- Issued **once**, at sign-up, in the sign-up response. Never retrievable afterwards.
- Stored only as `recoveryHash`. The plaintext exists in exactly one response body, once.
- **Single-use, enforced by a COMPARE-AND-SET on `recoveryHash`.** Consuming it rotates
  the hash and issues a *new* code in the same response, so a teacher who recovers is
  never left without a future recovery path.
  - The rotating hash is the version token: only the writer whose read is still current
    can land, so exactly one of N concurrent recoveries succeeds and the rest get
    `401 invalid_recovery`.
  - **`recoveryUsedAt` records WHEN the last code was consumed. It is not the guard.**
    The first implementation filtered on `recoveryUsedAt: null` while setting that same
    field to `null` in the same update — the guard guarded nothing, four concurrent
    recoveries all succeeded, and three teachers were handed a code that was already
    dead. Found by an adversarial probe, not by the oracle, because the oracle only
    replayed a consumed code sequentially.
- **Hand-transcribable, under RTL.** A teacher writes this on paper.
  - alphabet: `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — **Latin uppercase + digits, no
    `I O 0 1`** (transcription confusables).
  - shape: `XXXX-XXXX-XXXX` (12 chars, 3 groups). ~60 bits.
  - **Rendered LTR inside an RTL page** (`dir="ltr"` on that element) — an RTL-flipped code
    is a code a teacher copies down wrong.
  - Input is **case-insensitive and separator-insensitive**: uppercase and strip non-alphanumerics
    before hashing, so `abcd efgh ijkl` and `ABCD-EFGH-IJKL` both work.

## Error contract

Every error keeps the existing envelope: `{ error: { message, type }, correlationId }`.
**`message` is Arabic** (teacher-facing, per the hard constraints); `type` is the stable
machine key that `fe` branches on.

| Status | `type` | When | Retryable |
|---|---|---|---|
| 400 | `invalid_request` | malformed body, password < 8 chars, bad email shape | no |
| 401 | `invalid_credentials` | wrong email **or** wrong password, **or** the row is anonymous (no password set) | no |
| 401 | `invalid_recovery` | wrong/used recovery code | no |
| 409 | `email_taken` | sign-up on an existing email | no |
| 503 | `store_unavailable` | Mongo down | **yes** |

**Two rules that must not be relaxed:**

1. **`invalid_credentials` is returned for an unknown email *and* a wrong password**, with
   the same message and the same timing profile. Distinguishing them turns sign-in into an
   account-enumeration oracle — the same reasoning that made `getOwned` scope ownership
   inside the query (`store/subjects.ts:130-133`).
2. **`claude_auth` and `store_unavailable` are both 503 and mean opposite things.** `fe`
   branches on `error.type`, never on the status code. Pre-existing rule; restated because
   this contract adds a third 503 producer.

## What changes on an existing surface

Exactly one behaviour, and it is the point of gap #1:

**`requireTeacher` (`src/teacher.ts:41-52`) gains the ability to reject.** Today any
well-formed 32-hex id is accepted and owns nothing. Once a `teachers` collection exists, an
id that was never issued is rejected with `401 teacher_required` — the existing type, so the
error shape is unchanged.

> **This is a deliberate, declared supersession (WF-65).** The `persistence` job's promoted
> suites pin today's *acceptance* of an unknown id. That pin is superseded here, not
> regressed: the invariant it protected — a valid teacher reaches only their own subjects —
> is unchanged and strengthened. The amendment must be declared in the implementing
> sub-issue's journal, and the independent verifier checks it is legitimate supersession.

**Rate limiting is NOT in this contract.** `be` has no rate limiter and adding one is its own
decision. Recorded in SEED → Risks as accepted for this milestone.
