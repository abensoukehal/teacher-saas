## CI baseline — what that "green" actually means (read before trusting it)

> Recorded at PROVISION per the /provision step-4 review. Kept **outside** the
> generated block above, which is rewritten by every `tools/provision … verify`.

**The `green` in the receipt above is not earned, and it says nothing about this job.**

`tools/provision` computes the baseline with `tools/ci <key>` run **from the clone
root, with no `--slug`** (`tools/provision:85`). From there the engine resolves the
checkout to the *main* project dir, not this worktree — so it never sees
`feature/core-loop`, and with no slug it falls back to mainline mode and gates the
**promoted regression net** at `project/tests/<key>`. That directory is empty, so:

```
gate PASS  (0 ran, 1 skipped)        →  recorded as "green"
```

Run the same gate where the job actually lives and it disagrees:

```
cd project-worktrees/core-loop && ../../tools/ci all
gate FAIL  (0 ran for job 'core-loop' — a no-op gate must be red; 3 skipped)
```

Both are "correct" for what they measured. The receipt's is measuring the wrong
thing. **Treat this job's true CI baseline as: no tests exist yet, for either
stack — a no-op gate, i.e. red.** There are no pre-existing reds to carry (WF-50
trail is empty) because there are no pre-existing tests.

Consequences for this job:

- The first sub-issue on each stack has to *create* its gate; there is nothing to
  characterize against. New surfaces get spec-tests against the contract
  (`iterations/01-initial/contracts/`), not characterization tests.
- Do not read a later "green" from `tools/provision … verify` as progress. Gate
  this job with `tools/ci <key> --slug core-loop` **from this worktree**, which is
  strict (WF-68) and fails a no-op honestly.

**`tools/ci` itself works fine for `be` and `fe`** — it resolves both worktrees and
runs jest/vitest. Only its hardcoded third key `ai` is absent, which reports as
"repo not attached". An earlier note claiming `tools/ci` could not gate these keys
was wrong.
